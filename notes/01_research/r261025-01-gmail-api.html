概要とリソース

Gmail API は、Gmail のメールボックスの読み取り・送信・整理・設定変更を行う RESTful API。ユーザーの認可を得て Gmail データへ触れる Web アプリの、多くの場面で最適な選択肢とされている。

主なリソース

リソース内容
messages送信者・宛先・件名・本文を持つメール。作成後は内容を変更できない
threads関連するメッセージを会話としてまとめたもの
labels整理用の印。システムラベル (INBOX・TRASH・SPAM 等) は作成・削除できない。ユーザーラベルは作成・変更・削除できる
drafts未送信のメッセージ。内容を差し替えられる。送信すると下書きは消え、SENT ラベルのメッセージができる
historyメールボックスの変更履歴。historyId を起点に差分を取る (「プッシュ通知と送信」を参照)
settings送信元エイリアスと署名・転送・フィルタ・不在通知・S/MIME・POP/IMAP・委任・言語

できること

  • 読み取り専用でのメールの抽出・インデックス化・バックアップ
  • プログラムからのメール送信
  • フィルタによる振り分け・ラベル付け
  • 署名・転送などの設定管理 (組織全体での署名の標準化を含む)
  • メールボックスの変更通知 (Cloud Pub/Sub 連携)
  • 同じ Google Workspace 組織内での、別ユーザーのメールボックスへの委任

出典: Gmail API の概要 (Google for Developers)

認証とスコープ

認証情報の種類

種類Gmail での使いどころ
API キー公開データ用。Workspace の大半のデータは OAuth 2.0 が必要で、メールには通常使えない
OAuth 2.0 クライアント IDユーザー所有のメールに触れる主要な手段。同意画面での承認が要る。長期の利用にはリフレッシュトークンを取る

クライアントシークレットは、アプリのコードに平文で含めず安全に保管する。

スコープ

区分は Non-sensitive / Sensitive / Restricted の 3 段階。要る範囲だけを求める。

スコープ (https://www.googleapis.com/auth/ 以下)区分概要
gmail.labelsNon-sensitiveラベルの閲覧と編集
gmail.addons.current.action.composeNon-sensitiveアドオン操作時に下書きの管理とメール送信
gmail.addons.current.message.actionNon-sensitiveアドオン操作時にメッセージを閲覧
gmail.addons.current.message.metadataSensitiveアドオン実行時にメタデータを閲覧
gmail.addons.current.message.readonlySensitiveアドオン実行時にメッセージを閲覧
gmail.sendSensitiveユーザーの代理でメールを送信
gmail.readonlyRestrictedメールと設定の閲覧
gmail.composeRestricted下書きの管理とメール送信
gmail.insertRestrictedメールボックスへのメール追加
gmail.modifyRestricted閲覧・作成・送信。ゴミ箱を経由した即時の完全削除はできない
gmail.metadataRestrictedラベルやヘッダーの閲覧 (本文は不可)
gmail.settings.basicRestrictedメール設定とフィルタの閲覧・変更
gmail.settings.sharingRestricted重要な設定の管理。管理者用で、ドメイン全体の委任を受けたサービスアカウントのみ
https://mail.google.com/Restricted閲覧・作成・送信に加え完全削除も可能
IMPORTANT
メールを読むスコープ (gmail.readonly 等) は、本文を読めないはずの gmail.metadata まで含めて Restricted。送信だけなら Sensitive の gmail.send で足りる。https://mail.google.com/ は、即時かつ完全な削除が要るときだけ求めるよう公式が注記している。

クォータ

上限

種類上限
1 分あたり・プロジェクト1,200,000 ユニット
1 分あたり・ユーザー / プロジェクト6,000 ユニット
1 日あたり・プロジェクト (課金のしきい値)80,000,000 ユニット
  • ユーザー単位・プロジェクト単位の上限は「毎秒」ではなく毎分
  • 1 日 80,000,000 は速度制限ではなく、超えた分に課金が発生するしきい値。引き上げの申請はできない
  • 1 通あたりの受信者数は 500 人まで
  • 2026 年 5 月 1 日以降に作ったプロジェクトには新しいクォータが適用される。それ以前のプロジェクトは従来の設定のまま

プッシュ通知と送信

プッシュ通知 (watch)

  1. Cloud Pub/Sub にトピックとサブスクリプションを作り、gmail-api-push@system.gserviceaccount.com にトピックへの publish 権限を与える
  2. users/me/watch にトピックと対象ラベルを指定して呼ぶ。現在の historyId と expiration が返る
  3. 通知の message.data (Base64URL の JSON) にメールアドレスと新しい historyId が入る
  4. 保存しておいた前回の historyId で history.list を呼び、差分を取る。処理後に新しい値を保存する
  5. Webhook は HTTP 200 などで確認応答になる。pull は acknowledge を明示的に呼ぶ。応答が無いと再送される
WARNING
watch は 7 日以内に再実行しないと、そのユーザーの更新が届かなくなる。公式は 1 日 1 回の再実行を勧める。通知は通常数秒で届くが、まれに遅延・欠落するため、通知が来ないときの備えとして history.list の定期呼び出しを用意する。
  • 通知レートはユーザーごとに最大 1 秒あたり 1 件。超過分は破棄される
  • 通知の処理中に新しい通知を起こすと通知ループになりうる
  • インストール型アプリやモバイル端末などユーザー所有のデバイスには、公式はポーリングによる同期を勧める

出典: Gmail のプッシュ通知 (Google for Developers)

メール送信

1. RFC 2822 準拠の MIME メッセージを作る (添付はマルチパート)
2. base64url でエンコードして、メッセージの raw に入れる
3. messages.send (下書きなら drafts.send) を呼ぶ
  • 返信を同じスレッドにまとめる条件は、Subject の一致と、References・In-Reply-To の RFC 2822 どおりの設定
  • メッセージサイズの上限は、取得したページに記載が無かった。別の公式ドキュメントで確かめる

出典: メールの送信 (Google for Developers)
